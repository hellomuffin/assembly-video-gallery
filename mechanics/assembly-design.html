1Gravity was on. The connection happened too early.

The earlier motion prototype rigidly attached wood parts as soon as they were placed, before screws were installed. Those hidden attachments kept the bars suspended despite gravity.

Earlier prototype · incorrect causality

Place the rail→Attach it invisibly→Animate fastening

The rail stays up even though nothing has fastened it yet.

Required behavior

Hold or support→Align and fasten→Release and test

Before fastening, hands or real contact must support the part. Afterward, the connection must carry the load.

A physics-engine joint can be a useful approximation of a real connection. Activating it merely because a part reaches its destination is the error. A hinge, loose fit, and tightened connection also need different behavior.

2The hard part is the sequence between stable states.

A finished table can be stable even when an intermediate assembly step is impossible with the available hands and supports.

Example: attaching a table leg

  1. You hold the tabletop vertically.
  2. You bring a leg to its mounting point.
  3. One hand must hold the leg; another must operate the screwdriver.
  4. Something still needs to support the tabletop.
  5. When you release a hand, the remaining support must actually carry the weight.

A simpler solution: assemble the table upside down on the floor. Better task setup can eliminate a difficult balancing problem.

Access and handoff

  • A support can block the hand or screwdriver.
  • A useful pickup grasp can obstruct the final insertion.
  • Raising a support can disturb an aligned component.
  • Parts may need reorientation or a different grasp before fastening.

Fine contact and numerical cost

  • Rigid finger shapes approximate soft skin poorly.
  • A visually plausible grip can slip as the object rotates.
  • Extra squeezing can push a light part sideways.
  • Small contacts and stiff controllers require frequent physics updates.
Why the recent runs were slow
  • The detailed scene contains roughly 7,400 collision shapes.
  • Integration runs at up to 2,000 physics steps per simulated second.
  • Recent runs took roughly 10–15 wall-clock minutes per simulated minute; this is an observed range, not a universal benchmark.
  • Failures required replaying earlier motions, and sparse checkpoints caused additional repeated work.

Too much effort went into contact-only anatomical grasping before establishing reusable assembly execution. Runtime and recovery should have been addressed earlier.

3Simplify the mechanics without erasing consequences.

Bounded grasp assistance

  • The hand reaches a suitable location and closes.
  • A simplified grasp carries the object with declared load and motion limits.
  • Release removes the grasp.
  • An unsupported object falls.

This approximates dexterity. It does not authorize premature connections between furniture parts.

Simplified connector mechanics

  • Use alignment, insertion, engagement, and tightening states.
  • Relate screw rotation to engagement and advancement.
  • Use joint constraints appropriate to the connector.
  • Preserve loosening, incomplete insertion, and failed fastening.

Detailed thread-to-thread collision and muscle simulation are not prerequisites for these behaviors.

4Describe each furniture item. Reuse the executor.

The legacy stool pipeline contains furniture-specific part names, approach directions, and special cases. A separate shared core now executes table and shelf descriptions using the same action code. This demonstrates limited reuse; arbitrary CAD and new connector mechanisms still need work.

Changes with the furniture

Asset and connection description

  • Component geometry, mass, and collision shapes.
  • Candidate grasp regions and support surfaces.
  • Connection locations, local axes, and connector types.
  • Assembly relationships and task-specific metadata.

Shared across furniture

Execution and feedback

  • Grasp, carry, hold, align, insert, turn, release, and reposition.
  • Find reachable paths in the current scene.
  • Monitor contact, displacement, and operation progress.
  • Report failed or obstructed operations.
Example shared action: insert(component, connection, distance)

Compute motion from that connection’s local axis and geometry. Avoid a rule such as “move this stool rail 40 cm along world Y.”

A new furniture model should require a description and connector metadata, rather than a new motion script. A new connector mechanism may require another reusable implementation. Automatically inferring all this metadata from arbitrary CAD or a manual is a separate problem.

How to demonstrate generalization
  • Run the same executor on structurally different furniture: for example, a table, shelf, and cabinet.
  • Vary dimensions, initial component positions, and orientations.
  • Test release before fastening, wrong alignment, wrong parts, and reverse screw rotation.
  • Check that failures and recovery remain sensible without furniture-specific trajectory patches.

Renaming stool parts or replaying a fixed trajectory on a slightly different model would not establish this.

5The executor must not secretly solve the task.

A wrong instruction must remain capable of producing a wrong outcome.

If the assistant asks the user to pick the wrong board or turn the wrong screw, the simulator must not silently select the correct part or complete the intended assembly step.

  • Task decision: what the assistant asks the user to do.
  • User execution: how the simulated user interprets and attempts that instruction; this remains a separate layer.
  • Motion execution: how the requested movement is carried out within physical and reach limits.
  • Environment: what happens when the action succeeds, slips, collides, or fails.
  • Evaluation: whether the resulting state meets the task criteria.

Local motion planning can avoid an obstacle or report that a movement is blocked. It should not replace an incorrect assembly decision with the correct one. This preserves the interaction and recovery challenges the assistant is meant to solve.

Implementation priorities

  1. Retain the accepted visual presentation. Detailed anatomy is not the immediate bottleneck to solve.
  2. Preserve causal physics. Gravity, collision, support, and correct connection timing come first.
  3. Use explicit approximations. Simplified grasps and connectors are allowed and should be documented.
  4. Separate data from execution. Furniture descriptions supply geometry and connection information.
  5. Validate distinct furniture types. Demonstrate shared actions and meaningful failure cases.
  6. Improve dexterity and full-body physics later. Do not make them prerequisites for a useful interaction environment.
